**Google Antigravity** 最初是作为 AI 软件工程环境设计的。通常的用法是：打开一个代码仓库，发起一段对话，让 Agent 读文件、改代码、跑测试，直到把功能做完。

每天重度使用之后，我产生了一个更贪心的想法：**能不能把它改造成一个多任务个人 Agent？**

我不想再为每个项目、每件琐事开一堆不同的软件和窗口，而是希望有一个全天候在线的总工作区——无论在电脑前，还是出门在外用手机打开 Antigravity 的 Remote Control 远程界面，都能通过**同一个入口**，同时推进多个仓库的代码开发、投资研究笔记、收件箱整理，以及家里的日程提醒。

起初，我完全靠写提示词来组织这套流程。我建了一个总控工作区，在 `AGENTS.md` 里写下几条家规：*把主对话当成前台总控；简单问题当场回答；写代码和深度研究派发给后台子代理；把个人笔记整理好；发任何外部消息前先问我。*

在两三轮就能结束的简单测试里，这套规则运转得很顺利。但一到真实的多任务日常里，它就频频失灵。出门前你在手机主对话里随口问一句“为什么昨天那个构建挂了？”，模型会“顺手”读一个文件看看情况，接着发现一行报错，直接开始改代码、跑测试套件、修下一个编译警告。五分钟过去，手机屏幕上还在滚测试日志——而当你急着想查一下今天的日程、或者看一眼另一个项目的进度时，你的主入口已经彻底卡死了。

解决办法其实是一套简单的分工：**直接复用 Antigravity 的手机远程界面与后台子代理，再通过生命周期钩子挂上一个本地 Go 小助手来守住多任务边界——因为提示词只是建议，而钩子才是硬规则。** Antigravity 支持在每次调用工具前先运行我的本地程序；只要我的程序返回“不允许”，这次工具调用就根本不会发生。

![多任务个人 Agent 架构：前台主对话负责理解与派发，本地 Go 钩子护栏放行前 3 次轻量查询并否决直接改代码或跑测试，将耗时任务分流至后台子代理与各自独立的 Git Worktree 目录。](/diagrams/harness-frontdesk-zh.svg)

*前台主对话如何保持秒回：主对话专心接待与调度，本地 Go 钩子在每次工具调用前拦截重操作，迫使长任务转入后台并行推进。*

## 为什么不重造轮子，而是给 Antigravity 配一个 Go 小助手？

当提示词怎么都拦不住主对话被长任务拖住时，我也考虑过要不要换一套专门的开源个人 Agent 框架，或者自己从头写一个聊天服务端。

但仔细一想，那等于把 Antigravity 已经做得很成熟的能力全扔了。开箱即用的 Antigravity 本身就已经提供了：

- **手机端 Remote Control 远程界面**：不用自己写前端 App，在手机浏览器里就能直接顺畅交互。
- **后台子代理与多会话并行**：支持在后台拉起子代理或独立任务线程，干完活自动回报。
- **实时 Markdown 状态卡片**：可以在对话侧边固定一张实时刷新的任务看板。
- **生命周期钩子**：支持在会话启动前、每次调用工具前、以及每轮回答结束后执行本地程序。

我真正缺的并不是一套新的 Agent 引擎，而是一个**在排错上头时也不会忘事的“交通警察”**。

所以我保留了 Antigravity 作为交互界面和调度底座，只用 Go 标准库写了一个零外部依赖的 Go 小助手（我叫它 `hq`，即 headquarters 总控台），挂载到 Antigravity 的生命周期钩子上：让大语言模型专心负责**理解与判断**（听懂需求、写代码、做分析），而把**多任务隔离与安全边界**交给确定性的 Go 代码来执行。

## 一个永远不会被卡死的“前台主对话”

在只写一个项目的编码会话里，等 Agent 改完代码跑完测试花上几分钟是很正常的。但在多任务个人 Agent 里，置顶的主对话是你的**前台**——如果前台接待员亲自跑进机房修机器修上二十分钟，大厅里就再也没法接待新需求了。

在提示词里写*“遇到重任务请派发给子代理”*只是一句礼貌的建议。当一个 Bug 看起来改一行就能修好时，模型“马上帮人把活干完”的本能往往会压过那句建议。

一个本地小状态文件记录着我置顶前台主对话的会话 ID。只要工具调用发生在这个主对话里（后台子代理不受此限制），Go 小助手就会在工具执行前守住四条规矩：

1. **主对话禁止直接改代码或跑测试：** 只要当前处于前台主对话，任何直接修改源码或运行测试套件（`go test`、`npm test`、`pytest`）的工具调用都会在执行前被直接否决。
2. **每轮最多 3 次轻量查询：** 前台主对话每轮最多只能执行 3 次只读查看（比如查一下日历、看一眼任务状态或翻一条简短笔记）。一旦发起第 4 次查询，钩子就会立刻拦下，要求模型把任务交给后台子代理，或者在侧边栏拉起一个专门的任务线程。
3. **每个编码任务分配独立的 `git worktree`：** 当主对话把编码任务派发出去时，小助手会自动为它在独立目录里检出一个单独的分支（即 `git worktree`）。这样我可以同时让一个子代理重构工具、第二个子代理写博客、第三个子代理核对研究数据，不同任务的代码分支和未提交文件永远不会互相覆盖。
4. **后台静默刷新状态卡片：** 每轮对话结束时，钩子直接读取会话日志并自动刷新侧边栏固定的状态卡片——既不消耗任何额外的模型 Token，也不会在聊天窗口里刷满机械的进度表格。

加上这层机械约束后，主对话终于像一个真正的多任务总控台了：我可以先派发一个耗时的代码修复任务，下一秒接着问周四下午孩子的数学竞赛是几点，几秒钟就能拿到答复，而写代码的子代理在后台安静地并行推进。

## 当一个工作区同时管代码与生活，如何防止“串味”？

一旦同一个 Agent 同时接触你的开源代码、研究笔记、外部邮件和个人日程，另外三种碰撞很快就会浮现出来。

![防止多任务“串味”的三道边界：1. 启动索引（≤80行）、按需专题笔记与夜间核对；2. 外部文件隔离读取与绑定命令哈希的手机端一键确认；3. 私密 local/ 目录与公开代码树经提交前隐私门禁隔离。](/diagrams/harness-layers-zh.svg)

*按正文顺序展开的三道隔离边界：清晰划分哪些步骤由 Go 代码确定性卡死，哪些步骤交给模型按需判断。*

### 1. 不让长期记忆变成“杂物抽屉”

在之前关于[单卡 RTX 3090 运行本地 Qwen 编码 Agent](/zh/blog/local-qwen-opencode-3090/) 和[调优输出限制](/zh/blog/qwen-agentic-tuning-3090/)的实验里，每次任务都是独立的。但个人 Agent 需要跨越数周甚至数月记住上下文。

如果让模型每次干完活都自由往同一个 `MEMORY.md` 里追加笔记，用不了一周就会变成大杂烩：代码细节和家庭日程混在一起，过期的临时待办一直占着上下文；更糟糕的是，如果模型某次*误以为*自己修好了某个问题，它会把这句未经核实的“已修好”当成事实写进长期记忆里。

为此，这套方案把记忆管理拆成了“Go 代码定规矩”和“夜间模型做复核”两部分：

- **精简的启动索引（不超过 `80` 行，由 Go 强制检查）：** 每次新会话启动时，只加载一份极短的当前重点清单和专题目录，Go 小助手会检查确保这份启动索引绝不超出 80 行。
- **按需读取的专题笔记：** 软件项目架构、投资逻辑跟踪、家庭日程安排分别存放在独立的专题文件里，只有聊到相关话题时才会按需加载。
- **夜间静默核对任务：** 每轮对话的原始工具输出与摘要由钩子自动落盘，不消耗额外模型调用。每天深夜，后台定时运行的模型核对任务会把当天的对话摘要与真实执行的原始工具输出逐一比对，核实无误后才更新到长期专题笔记中，并把需要关注的事项汇总进第二天早上的晨报。

### 2. 看外部消息与对外发消息必须分开

当一个 Agent 既能读取外部发来的邮件或文件，又拥有发消息、合代码的工具权限时，不可信文档里夹带的隐藏指令就有可能诱导模型误触外发操作。

当不可信文本和你的指令处在同一个上下文窗口里时，只靠提示词叮嘱*“发消息前一定要先问我”*是很脆弱的。Go 小助手通过两步把“读”和“做动作”隔开：

- **隔离清洗作为第一道过滤：** 外部收件箱文件和邮件必须通过专门的包装命令打开，剥离明显的指令诱导格式并打上不可信数据标记。当然，基于规则的文本清洗只能算尽力而为的第一道过滤——没人应该指望靠正则匹配彻底解决提示词注入——所以真正的外发动作绝不能只靠它把关。
- **绑定命令哈希的手机端一键确认（真正的安全边界）：** Agent 无法直接执行任何不可逆的外部动作（如发送邮件、发送 Google Chat 消息或合并 Pull Request）。它必须先调用 Go 小助手生成一份锁定完整命令哈希值的提案，并在手机上弹出单选题确认卡片。只有当我点下**批准**，Go 小助手校验命令哈希值完全一致后，才会真正执行那条命令。

### 3. 通用底座代码与个人私密文件分层存放

个人 Agent 必须读得到你的真实笔记、日程和财务底稿才真正趁手；但如果这些个人文件跟通用的 Agent 脚本放在同一个 Git 仓库里，一次粗心的 `git add .` 就可能把隐私数据推到公开仓库上。

因此工作区采用了严格的**双层目录隔离**：

- 根仓库只放通用的 Go 小助手源码、工作流技能模板和说明文档。
- 所有个人笔记、财务底稿、记忆文件和并行任务工作树，全部存放在被根仓库忽略的 `local/` 目录下，由独立的私有 Git 仓库单独备份。每次提交和推送前，Go 小助手都会自动运行 5 项隐私检查，确保没有任何个人目录文件、本机路径、私人邮箱或密钥混入公开代码树。

## 当 Agent 自己也会改工作流规则时，谁来守住护栏？

因为我平时也会让这个 Agent 帮我总结日常摩擦、直接提议并修改它自己的工作流技能文件，一个很现实的问题就来了：**如果 Agent 在更新技能文件时，不小心把某条安全或隔离规则改坏了怎么办？**

我原本写了一套覆盖 18 个完整多任务工作流的沙箱测试——在独立的临时目录里真实模拟前台查询上限、隐私扫描、记忆更新和手机审批。但最初我没有把它放进每次 `git push` 的自动检查里，因为 18 个测试沙箱每次都会各自从头编译一遍 Go 小助手，跑完一轮要 **`10.5 秒`**。当好几个后台子代理同时在不同分支上提交代码时，每次推送都卡上十秒钟显得有些拖沓，于是那套慢测试就被留成了手动按需运行。

结果，就在 Agent 第一次自动修改一份工作流技能文件时，改动意外打破了一条测试结构假设；而因为跳过了那套耗时 10.5 秒的沙箱测试，那次有问题的提交被直接推上了主分支。

![编译一次 Go 小助手并复用到 18 个测试沙箱后，工作流测试耗时从 10.5 秒降至 1.8 秒（耗时减少 82.9%，快了约 5.8 倍），使每次推送前都能在约 2.5 秒内自动跑完 5 项隐私检查、18 次钩子越界模拟和 18 个完整沙箱测试。](/diagrams/harness-ci-zh.svg)

*在单次测试运行中只编译一次 Go 小助手并共享给 18 个隔离沙箱后，沙箱测试耗时从 10.5 秒降到了 1.8 秒（耗时减少 82.9%，快了约 5.8 倍），从而能直接挂进每次 `git push` 自动执行。*

修复方法非常简单：在测试套件启动时只编译**一次** Go 小助手，然后把编译好的二进制文件复制到每个测试独立的临时沙箱里。这一改，18 个沙箱工作流测试的耗时直接从 **`10.5 秒`降到了 `1.8 秒`——耗时减少 82.9%（快了约 5.8 倍）**。

当核心沙箱测试跑完不到两秒钟，我就直接把它和其它快速检查一起挂进了每次 `git push` 的自动门禁里。现在无论是人还是后台子代理推送代码，都会在**合计约 2.5 秒**内自动跑完三道检查：

- **5 项隐私与路径检查：** 确保公开仓库里没有任何私密目录文件、本机路径或密钥泄露。
- **18 次钩子越界模拟：** 模拟前台主对话超额查询、直接改代码和未授权外发，验证钩子能 100% 拦下。
- **18 个完整沙箱工作流测试（`1.8 秒`）：** 在干净的临时沙箱里把多任务核心流程从头到尾跑通一遍。

## 哪些地方仍然会出问题？

给 Antigravity 加上这层 Go 小助手之后，主对话卡死和任务互相覆盖的问题基本消失了，但它并不是银弹。在日常使用中，仍然有三处真实的摩擦点：

1. **“最多 3 次查询”是一把比较粗的尺子。** 有时候我在手机上问一个确实很简单的日常问题，恰好需要读第 4 个文件才能拼出完整答案。钩子在拦下第 4 次读取后，主对话只能被迫拉起一个后台子代理去查，反而让本来再花五秒就能答完的小问题多了一次转交等待。
2. **命令行匹配总有边缘情况。** 拦住文件编辑工具和常见的测试命令（`go test`、`npm test`、`pytest`）能挡住绝大多数顺手改代码的冲动，但模型偶尔还是会拼出一条不在黑名单里的复杂 Shell 管道命令，需要我在发现后继续补进拦截规则。
3. **干净的目录隔离，代替不了清晰的派单说明。** 钩子能强迫前台主对话把编码任务派发给后台子代理，但如果主对话在派单时只写了两句含糊不清的任务描述，后台子代理依然会写错方向——只不过是在它自己干干净净的 `git worktree` 里安静地写错而已。

## 这套改造给日常使用带来了什么改变？

给 Google Antigravity 配上这个小巧的 Go 小助手，并不会让底层的大语言模型变得更聪明。当后台子代理去排查一个复杂的并发 Bug、或者分析一份长篇财报时，最终结果的好坏依然取决于模型本身的能力和任务定义——这和我在[决策模型后训练实验](/zh/blog/decision-model-after-b2/)中看到的是同一个道理。

它真正改变的，是**同一个 Agent 工作区能不能同时装下你一整天的不同任务，而不自己绊倒自己**：

- 你可以让后台跑着好几分钟的代码修改或深度研究，同时在手机主对话里随时穿插查日程、记想法，几秒内得到回复。
- 不同代码仓库、个人笔记和长期记忆各归各位，不会在同一个上下文窗口里越滚越乱。
- 发消息、合代码等外部动作稳稳停在手机端的一键确认之后，私密笔记也绝不会因为一次误操作漏进公开提交。

如果你也在把身边的 AI 编码工具改造成更顺手的个人日常助手，每当你想往 `AGENTS.md` 里再加一条叮嘱时，不妨先问自己一句：

> **这条规则只是一个写作风格上的偏好，还是一道防止多任务互相打架的隔离墙？如果是后者，能不能写几行简单的钩子代码，让环境自动替你守住它？**

- **零 Token 状态卡片与日志：** 每轮对话结束时，Antigravity 的 `Stop` 钩子调用 `./bin/hq hook stop` 直接用 Go 解析会话 JSONL 轨迹文件，在 `0` 额外模型 Token 消耗下自动更新侧边栏的 `hq_console.md` 状态卡片与每日回合日志（`local/memory/journal/`）。
- **分层记忆、审批哈希与隐私扫描：** 启动记忆索引（`local/MEMORY.md`）限制在 `<= 80` 行，指向按需读取的专题文件（`local/memory/topics/*.md`）与带时间戳的事实记录（`local/memory/facts.jsonl`）。外发动作通过 `./bin/hq propose` 生成锁定完整命令 `SHA-256` 哈希值的提案，并在人工确认后由 `./bin/hq approve <id> --sha256=<prefix>` 校验执行。提交与推送前的隐私扫描器检查 5 类边界（`5/5`）：无 `local/` 或私钥文件、无硬编码本机用户路径、邮箱白名单检查、无 API/OAuth 密钥特征、以及无本地私密词条泄露。
- **测试提速（`10.5s → 1.8s`，快了约 `5.8` 倍）：** 在端到端测试中通过 `sync.Once` 只编译一次 `bin/hq` 并复制到 18 个隔离的临时沙箱目录中，将 `go test ./internal/e2e` 耗时从 `10.5 秒`（每个测试单独 `go build`）降至 `1.8 秒`（耗时减少 `82.9%`，提速约 `5.8` 倍），从而让隐私边界扫描（`5/5`）、钩子越界模拟测试（`18/18`）和端到端沙箱工作流测试（`18/18`）能够在每次 `.git/hooks/pre-push` 时于约 `2.5 秒`内自动跑完。
